## 1. Where each label on these rows comes from, and why the D130-2 rebuild did not recompute it

All 11 rows are legacy seeds (`legacy/incidents.json`, plus one table row and one ATLAS case study on INC-02899). Field by field,
read from `scripts/parse_existing.py` and `scripts/merge_and_dedupe.py`:

| field | origin for these rows | why the rebuild left it on the old text |
|---|---|---|
| `owasp_llm`, `owasp_asi`, `owasp_dsgai` | hand codes in the seed's `owasp_entries` (`parse_existing.normalize_owasp`); unioned across merged sources by `merge_into` | they are seed data, not computed from text; no step reads the description |
| `nist_ai_rmf`, `mitre_atlas` | computed from the OWASP codes by `parse_existing.derive_atlas_and_nist` plus an attack-vector "hint", then `fill_taxonomy` (merge step 1/4c) | computed from seed codes and the seed's raw `attack_vector` text, which D130-2 did not touch |
| `mitre_atlas_tactics` | `fill_taxonomy` from the final technique set (pinned ATLAS) | follows `mitre_atlas` |
| `attack_vector` | the seed's free-text `attack_vector` reduced to a hint key or its first word, then `_ATTACK_VECTOR_NORMALIZE`; only if that yields `other` does step 4b run `classify_attack_vector` on title + description | step 4b runs BEFORE the step-4d curation override, so it sees the OLD title/description. Where the seed word was not `other` (INC-02774 and INC-04955 `rce`, INC-02899 `insecure`→`auth-bypass`, INC-03004 `adversarial`→`adversarial-input`) no classifier runs at all |
| `severity` | the seed's hand value; `merge_into` keeps the maximum across merged sources | seed data |
| `category` | the seed's hand value (first source) | seed data |
| `tags` | the seeds' hand tags, unioned across merged sources | seed data |
| `maestro_layers` | the first seed's hand list, with free-text `notes` | seed data |
| `corpus` | step 5 `_classify_corpus` on title + description + tags, AFTER the override | the one label that already follows the new text (D130-2 pinned it on INC-02454) |

The gate's correction holds: for these rows the stale labels are seed data, not output of a description classifier. Two findings
come out of this table:

- **A substring artifact in `parse_existing`.** The attack-vector hint is a substring test (`k in av_lower`), so the key `rce`
  matches inside "enfo**rce**ment". INC-035 and INC-043 ("Not adversarial - regulatory enforcement; ...") became
  `attack_vector: rce` and got `AML.T0049`, `AML.T0050`, `MANAGE-2.3`, `MEASURE-2.7` from it, on two GDPR fines. The same artifact
  is on 3 rows outside this task (INC-02549, INC-04263, INC-02186; command in section 6). Not fixed here: changing
  `parse_existing` would move those rows.
- **Three of the rows are over-merges of two different legacy incidents.** INC-02454 = INC-036 (Clearview BIPA) + INC-039 (NYT v
  OpenAI copyright); INC-02774 = INC-035 (Garante decision) + INC-050 (noyb right-to-erasure challenge); INC-04179 = INC-044
  (Sama labelling workforce) + INC-048 (AI companion apps). The second seed's tags, codes, mitigations and (INC-04179) severity
  are unioned into the row. This is why INC-02454 carries `nyt`/`openai`/`fair-use` and INC-04179 carries `character-ai`/`replika`
  and `Critical`.

## 2. Method

Recompute, don't guess: `build_overrides.py` re-runs the build's own label code on each row's contributing sources (legacy seed
re-parsed with `parse_existing`; ingest rows through `normalize_entry`; union and max-severity through `merge_into`;
`classify_attack_vector` on the D130-2 title + description; `seed_frameworks_from_vector` + `fill_taxonomy`). `relabel_spec.py`
declares the only inputs that differ from the base build, each with its basis:

- **provenance**: a merged seed that describes a different incident is dropped (INC-039, INC-050, INC-048, and on INC-02899
  the table row LEGACY-INC-00149 whose whole text is the "public by default, no authentication" claim D130-2 removed). Its
  tags are removed only if no kept source carries them (checked by the script).
- **unsupported**: an OWASP/DSGAI code, tag or MAESTRO layer whose basis is a claim that is in the old text and not the new
  (D130-2's "description before/after" and "dropped" lines). Tags and MAESTRO layers are removal-only: nothing is added, no
  note is rewritten.
- **hint artifact**: the `rce`-in-"enforcement" hint is suppressed on INC-035 and INC-043.
- **judgement** (agent-suggested): three `attack_vector` values and one `category` where the rule's output is wrong or absent;
  each states the rule's own output next to the chosen value.

**Control (agreement 6).** With nothing dropped and the seeds' original attack_vector text, the same code reproduces BASE's
`owasp_*`, `nist_ai_rmf`, `mitre_atlas`, `mitre_atlas_tactics`, `severity`, `attack_vector` and `tags` on all 11 rows; the script
refuses to write otherwise. Seen to fire: deleting one technique from BASE INC-03972 fails it on that row and field, and
removing the `rce` hint key fails it on exactly INC-02774 and INC-04955 (which also confirms those labels came from the hint).
The delta gate (`delta.py`) was seen to fire the same way (exit 1 with a row taken out of scope and `tags` undeclared).

**Severity.** The repo has no text-based severity rule (WS2-T5's rubric is not built). Severity is therefore recomputed only as
the build does it, the max over the kept sources: INC-04179 goes Critical -> High because Critical came from the dropped INC-048.
The other rows keep the seed author's value. Rows whose severity was set against text that D130-2 changed, for WS2-T5:
INC-04955 (Critical; set with the EUR 12B Project Clover context), INC-04221 (Critical; set for synthetic CSAM generation),
INC-04653 (High; set for leaked secrets), INC-02899 (Critical; set for unauthenticated public agents; an ATLAS source also says
Critical).

**Rule outputs kept although imperfect.** INC-04221 stays `csam-generation`: the new text reports CSAM in a training dataset,
not generation, but the corpus uses that value for CSAM-topic rows and nothing better exists in the vocabulary. INC-02899 stays
`prompt-injection` (ATLAS's case study maps the same attack to indirect injection `AML.T0051.001`). INC-04221 keeps the
`stability-ai` tag (the new text names Stable Diffusion). DSGAI codes on the primary seeds are kept unless the repo's own text
ties a code to a dropped claim (DSGAI20 = data localisation, DSGAI07 = secrets): no DSGAI vocabulary is committed in the repo
(`docs/audits/brief-triage-2026-10-14.md`), so the rest cannot be checked against the new text here.

## 5. Mechanism: overrides freeze these labels. Acceptable here; a better mechanism exists

Only fields whose recomputed value differs from the base are written, so 9 rows have a label override and the untouched fields
keep following the build. Freezing costs little on these rows, because their labels were already seed data that no rule
re-derives; a future change to `classify_attack_vector`, the OWASP->ATLAS/NIST tables or the vector seeding will not reach the
overridden fields. A future ATLAS re-pin is caught, not missed: an overridden id that leaves the pin fails `lint_atlas_ids.py`
(override values are applied after `fill_taxonomy`, so `atlas_id_translations.json` does not translate them).

Recommendation (not built): apply the TEXT fields of a curation override (`title`, `description`) before step 4b instead of at
4d, and add an override flag (e.g. `"_relabel": "from-text"`) that makes the build ignore the seed's raw `attack_vector` and
re-run 4b/4c on the overridden text. That would have fixed `attack_vector` and the vector-seeded mappings on these rows with no
frozen values. It would not fix hand codes, tags or MAESTRO notes inherited from a wrong or over-merged seed, so a provenance
step like this one stays needed. It is a pipeline change (pipeline-engineer), with its own delta.
