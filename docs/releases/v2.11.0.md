## Headline — an over-merge is undone: 301 rows split back out, five published IDs stop resolving to themselves

> **Correction, 2026-09-20, before this document was gated.** An earlier
> draft of this file said "four IDs permanently retired" throughout,
> following its drafting brief. **A parallel measurement caught what
> neither the brief nor this document's first re-derivation checked**: a
> plain diff of the live ID set between the `v2.10.0` tag and this tree
> shows **five** IDs, not four, no longer resolving to themselves —
> `INC-00311`, `INC-00554`, `INC-00754`, `INC-01897`, **and `INC-07738`**.
> The first four are D28's authorized retirements. `INC-07738` is a
> separate, ordinary `reason: "merged"` tombstone into `INC-14757` —
> pre-existing dedupe behaviour unrelated to the D28 authorization, not
> one of the 47 rows that authorization covers. Both statements below are
> now stated distinctly rather than merged into one number, because they
> answer different questions: which IDs did D28 authorize retiring
> (four), and which published IDs actually stopped resolving to
> themselves in this release (five).

A query-string over-merge bug in `normalize_url()` had been silently
collapsing unrelated incidents together under a single shared published ID
whenever their source URLs differed only by query string — the corpus's
most similar pair by this measure, `INC-01192`, was four distinct VS Code
extension CVEs collapsed by nothing more than an `?itemName=` parameter.

**Concretely, because the abstract description understates what this
actually did to two rows anyone might already be citing:** `INC-00311`
(titled, before this fix, *"AI-Driven Military Targeting Causes Mass
Casualties in Middle East Conflicts"*) had absorbed an unrelated **Greek
tax authority AI** story (now its own row,
[`INC-14907`, "Greek Tax Authority Plans AI System to Combat Tax
Evasion"](https://github.com/emmanuelgjr/genai_incidents/blob/main/data/incidents.json)).
`INC-00754` (a **ChatGPT** case, *"ChatGPT Was Alleged to Have Aided
Planning of Florida State University Mass Shooting"*) had absorbed an
unrelated **Jason Momoa deepfake romance-scam** story (now its own row,
[`INC-14909`, "Purportedly AI-Generated Jason Momoa Deepfake Used in
Romance Scam Reportedly Defrauding British Widow of
$600,000"](https://github.com/emmanuelgjr/genai_incidents/blob/main/data/incidents.json)).
Neither absorbed story shared any real connection with its host incident
beyond a coincidentally-matching base URL.

The fix landed in two parts, both merged: `normalize_url()` itself
([`75825299`](https://github.com/emmanuelgjr/genai_incidents/commit/75825299791953f59d76c41b5ec94cb878cea8fa)),
and its reapplication plus a re-key of a mis-keyed `CVE-2025-10875`
curation override that the fix's own CI run surfaced
([`be547ae1`](https://github.com/emmanuelgjr/genai_incidents/commit/be547ae123c3cd5d5135534756c010dc2a78a176),
[`d463c3d4`](https://github.com/emmanuelgjr/genai_incidents/commit/d463c3d485134c2934cf839f381d395aaae36afe)).
Fixing the merge key alone does not retroactively un-merge the 301 rows
the bug had already collapsed in the *published* corpus — that required a
separate, irreversible data operation, deliberately held for its own
ruling because it retires published IDs. **The user authorized that
remediation as board decision D28 on 2026-09-18**, after review of
per-entity evidence for all 47 affected published rows
([`docs/audits/WS4-T19-authorized-splits-2026-09-18.json`](https://github.com/emmanuelgjr/genai_incidents/blob/main/docs/audits/WS4-T19-authorized-splits-2026-09-18.json),
55 entries — 47 splits plus 8 pre-existing inbound redirects the splits
touch). The unmerge itself executed in
[`f38a5d40`](https://github.com/emmanuelgjr/genai_incidents/commit/f38a5d40943468c0be5735ac2a21afcf67fa2b3e),
merged to `main` at
[`8f74b035`](https://github.com/emmanuelgjr/genai_incidents/commit/8f74b03514fbdf00b12bd1fda9a1581cbc6de5d2).

### What shipped, all of it verifiable from the repository

- **13,060 → 13,361 entries (+301).** 306 new IDs minted, 5 removed from
  the live set — the arithmetic is exact (`13,060 + 306 − 5 = 13,361`),
  independently re-derived by diffing the live ID set between the
  `v2.10.0` tag and this tree, not merely from the entry-count delta.
  These two claims are distinct and both true:
  - **D28 authorized and executed four retirements.** Of the 47 published
    IDs the remediation touched, **43 keep their identity** (`keep_id`
    splits — the row survives under its existing ID, and the content it
    no longer represents moves to new IDs). **4 were permanently
    retired** — `INC-00311`, `INC-00554`, `INC-00754`, `INC-01897` —
    because the row mechanically inheriting the old ID was not, in fact,
    its real successor; no `keep_id` choice was defensible for any of the
    four.
  - **Five published IDs stopped resolving to themselves in this
    release** — the four above, plus `INC-07738`, retired via an
    ordinary `reason: "merged"` tombstone into `INC-14757`
    (`retired_source_ids: ["OECD-AIM-2026-04-08-e597"]`). This is
    **pre-existing dedupe behaviour, not part of the D28 authorization**
    — it is the same Mythos cross-successor merge the WS4-T21 delta audit
    names as "ordinary, unrelated" — but it is exactly as real a
    stop-resolving-to-itself event for a consumer citing `INC-07738` as
    the four D28 retirements are, so it is named here rather than folded
    silently into "four."
- **8 existing inbound redirects were corrected.** 4 needed new
  `data/id_deprecations.json` records (three corrected redirects that had
  been fanning out through an over-broad `resplit` target, one corrected
  from resolving through a `keep_id` survivor that held only part of the
  original content). The other 4 already chain-resolved correctly once
  the 4 retirements above were in place, and needed no new record.
- **Every retired ID still resolves** through
  [`data/id_deprecations.json`](https://github.com/emmanuelgjr/genai_incidents/blob/main/data/id_deprecations.json) —
  1,051 → 1,060 records (**+9**), append-only under invariant 9 (no
  existing record edited or removed; checked directly, byte-identical).
  **No citation of any ID this project has published ever breaks.** This
  is not a softened claim — it is the promise
  [`docs/ID_POLICY.md`](https://github.com/emmanuelgjr/genai_incidents/blob/main/docs/ID_POLICY.md)
  makes, and this release keeps it through an irreversible 301-row change.
  **Two counts over that file now diverge for the first time in its
  history, and if you cite a deprecation count you should say which one
  you mean:** 1,060 *records*, but only **1,056 distinct `from` IDs** —
  four IDs (`INC-07771`, `INC-08109`, `INC-08133`, `INC-08146`) each carry
  **two** tombstones: an original `merged` record from 2026-06-28, and a
  `resplit` record from 2026-09-18 that supersedes it with the
  D28-corrected successor (this release's redirect-correction bullet
  above). Neither record was deleted — invariant 9 forbids it — so both
  are live, and a naive `len()` over the file double-counts those four
  IDs if you meant "how many distinct IDs have ever been retired."
  Reason breakdown across all 1,060 records: `out-of-scope` 704,
  `merged` 289, `orphaned-ingest-source-retired` 59, `split` 4,
  `resplit` 4.
- **`landmark_count` 1,905 → 1,915 (+10)**, and the decomposition is what
  makes that figure safe to publish rather than merely plausible:
  **−2** retired landmark rows, **+12** new landmark rows among the 306
  brand-new IDs, and **0** existing rows flipped tier in either direction.
  Entirely a consequence of the split, not a re-classification of any
  entry that was already published.
- **`tier` now ships in every distributed variant** — `data/incidents.min.json`
  (and the site and PyPI copies of it), the Hugging Face export, STIX
  (`x_tier`), and the MISP feed. It previously existed only in the full
  `data/incidents.json`, so the landmark count README tells readers to
  cite **could not be reproduced** from anything else this project
  distributes; it now can, at 1,915, from any of them.
  **A known gap remains, deliberately deferred and already registered:**
  the site's CSV export still lacks a `tier` column
  (`tests/test_landmark_distribution.py` holds that one case as
  strict-xfail until it lands).
- **A build-time authorization guard** now aborts before writing whenever
  a previously-single published ID would newly resolve to more than one
  row, unless the write is authorized by a list carrying the D28 approval
  marker — closing the gap where an earlier draft of the same guard read
  the authorized-list file **by filename**, which is satisfied by mere
  file presence rather than by an actual ruling. `tests/test_merge_and_dedupe.py`
  carries **13 dedicated tests** covering it: **9** exercise the
  split-authorization check directly (7 asserting it aborts on a distinct
  malformed/tampered-authorization input — including tamper-plus-recompute,
  closed by pinning the expected hash —
  `REQUIRED_SPLIT_AUTHORIZATION_ENTRIES_SHA256` in
  `scripts/merge_and_dedupe.py` — rather than trusting a file on disk; 2
  confirming the guard does NOT fire on a legitimate authorization or an
  ordinary merge), and **4** more cover the retirement/resplit-correction
  paths it gates. File presence authorizes nothing.
- **`generated` moves to 2026-09-18**, and the weekly refresh is unblocked
  for the first time since **2026-07-27** — the corpus count had not moved
  in that window first because of an unrelated silently-dead CI persistence
  step (fixed in v2.10.0), and then because the OECD AIM refresh freeze
  (board ruling D25(a)) held pending exactly this fix.

### Consumer impact, stated without hedging

**Anyone holding v2.10.0 or earlier has a corpus where `INC-00311`,
`INC-00554`, `INC-00754`, and `INC-01897` point at content that is not
theirs** — each of those four D28-retired IDs, in every release up to and
including `v2.10.0`, resolves to an over-merged row that conflates two or
more unrelated incidents. **A fifth ID, `INC-07738`, also stops resolving
to itself in this release** (an ordinary, unrelated `merged` tombstone
into `INC-14757` — see above); anyone holding that ID from `v2.10.0` or
earlier should re-resolve it too, through the same mechanism. **Anyone
joining or diffing on incident IDs across versions must re-resolve
through
[`data/id_deprecations.json`](https://github.com/emmanuelgjr/genai_incidents/blob/main/data/id_deprecations.json)** —
an ID that was valid and singular in `v2.10.0` may now be a retirement
record pointing at up to 100 successor rows (`INC-00554`'s case), and a
naive join on the literal ID string will silently under-count or
mis-attribute.

## The tier field, everywhere it now ships

A figure a consumer is told to cite must be selectable from the artifact
they actually hold. Before this release, `landmark_count` (1,915) was only
reproducible from `data/incidents.json` — the full file — because `tier`
did not exist on any slim or exported variant. It now ships on:

| Variant | Where `tier` appears |
|---|---|
| `data/incidents.json` | `tier` |
| `data/incidents.min.json` (+ the site and PyPI copies of it) | `tier` |
| Hugging Face `incidents.jsonl` | `tier` |
| `data/incidents.stix.json` / TAXII mirror | `x_tier` |
| MISP feed | `genai-incidents:tier="…"` tag |
| Site CSV export (`docs/app.js`) | **not yet** — deliberately deferred, sequenced after this rebuild so it did not ship a blank column in the meantime |

Full field reference and reproduction recipe:
[`docs/DATA_DICTIONARY.md`](https://github.com/emmanuelgjr/genai_incidents/blob/main/docs/DATA_DICTIONARY.md#reproducing-the-landmark-count).

## Two disclosures this release would be dishonest to omit

### 1. This is a data-integrity fix, not new coverage

The +301 entries are **not** newly-discovered incidents. They are content
that was always part of the corpus's inputs, previously hidden inside four
(and, before the wider 43-row `keep_id` set, effectively 47) over-broad
published rows because a merge key was too permissive. Do not read the
entry-count increase as evidence this release expanded source coverage —
see v2.10.0's own operational-fix section for the actual coverage work
(the truncation fix, the crawl-budget fix), which predates this release.

### 2. The version-string gap this document itself is evidence of

As stated in the banner above, every version string in the repository
still reads `2.10.0` as of this writing, and the `v2.10.0` **git tag**
points at a 13,060-row snapshot with zero retirements — a snapshot that
disagrees with what `main` (and, transiently, anyone who cloned `main`
between 2026-09-18 and this cut) actually serves. This document exists
specifically so that gap is disclosed and reviewable before the cut
closes it, per `docs/VERSIONING.md`'s own reason for requiring release
notes to be written and gated *before* any version string moves.
