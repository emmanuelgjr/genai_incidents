## Read this first: behaviour changes

Seven things change what an existing consumer observes. None removes a row and
no `INC-*` ID is removed or re-pointed (`data/id_deprecations.json` is
unchanged: 1,084 records in both releases).

### 1. `load_incidents()` no longer returns retracted or unverified rows by default (D134(i))

`genai_incidents.load_incidents(include_retracted: bool = False)` now drops rows
whose `status` is `retracted` or `unverified`, so `len(load_incidents())` equals
`incident_count`. `disputed` rows are kept (they are counted in
`incident_count`). `include_retracted=True` returns every row; the parameter
keeps its ruled name although it now also governs `unverified` rows. `query()`,
`by_id()`, `by_cve()` and the `resolve_*()` functions are **unchanged and still
read every row**, so an ID that resolves through them may be absent from
`load_incidents()`.

| Call | v2.13.0 | v2.14.0 |
|---|---:|---:|
| `len(load_incidents())` | 15,666 (every row) | **15,990** |
| `len(load_incidents(include_retracted=True))` | (parameter did not exist) | **16,031** |

Code that called `load_incidents()` and counted or iterated rows now sees fewer
rows (the 29 retracted plus the 12 unverified). To keep the old result, pass
`include_retracted=True`. The slim `incidents.min.json` is unchanged in shape
and still carries every row, with its `status`.

### 2. A new `status` value, `unverified`, and a new count (D130)

12 rows carry `status: unverified` with `status_reason.code:
no-confirmed-source`: an entry whose references turned out not to be sources for
it and for which no confirmed primary source was found after a documented
search. They are treated like `retracted`: kept in `data/incidents.json` with
the ID resolvable, **outside `incident_count`**, omitted from the site and from
the STIX, TAXII, MISP and Hugging Face exports. `unverified_count` is a new key
in `data/stats.json`, the build manifest, and the envelope of
`data/incidents.json` and every `incidents.min.json` (always present, 0
included). A strict validator built on the v2.13.0 schema rejects the new enum
value; use the v2.14.0 schema.

**The count identity changes.** The v2.12.0 and v2.13.0 notes check
`incident_count + retracted_count == len(incidents)`; that is **wrong for this
release** (it gives 16,019 against 16,031). The identity is
`incident_count + retracted_count + unverified_count == len(incidents)`.

### 3. Counts that moved are labelled `<release>+main` between releases (D132)

Between releases `data/stats.json` `version`, the build manifest, the slim
files' `version_label`, `INCIDENTS.md`, the README badge cell, the Hugging Face
card and the site header read `<last-release>+main`, and the plain version only
when the rows equal the release's. At this cut the suffix is dropped. A
consumer that matched `version` exactly against a release string between
2.13.0 and now saw `2.13.0+main`. The package version strings
(`pyproject.toml`, `CITATION.cff`, `.zenodo.json`, the User-Agent) stay plain.
`data/stats.json` gains a `last_release` object. The build-manifest schema
now **requires** `unverified_count`, `taxonomy_versions.owasp_dsgai`,
`.maestro` and `.nist_ai_rmf`, so a v2.13.0 `build_manifest.json` fails
the v2.14.0 schema on exactly those four keys; validate each manifest against
the schema shipped with it.

### 4. MITRE ATLAS pin 2026.09 to 2026.10: 1,740 rows change `mitre_atlas` (D149, D151)

`taxonomy_versions.atlas` is `2026.10`. Five technique ids were retired
upstream (`AML.T0024.000`, `.001`, `.002`, `AML.T0056`, `AML.T0057`).
Anything filtering on them must use the successors: `AML.T0057` becomes
`AML.T0085.002`, `AML.T0056` becomes `AML.T0085.003`, `AML.T0024.001` becomes
`AML.T0137.002`, and affected rows gain tactic `AML.TA0009` and lose
`AML.TA0010` where nothing else achieves it. **`AML.T0024.002` has no stated
successor** and is generalised to its parent `AML.T0024` on 4 entries; a
semantic re-target awaits label-scientist review. The old ids stay in the pin
marked `deprecated`. Measured against the v2.13.0 tag, 1,740 existing rows
differ in `mitre_atlas` and 1,739 in `mitre_atlas_tactics` (the merge-time
audit's 1,744 was measured against a base that included rows new since the
tag; see Verification). No row is added, removed or re-IDed by the re-pin, and
on a changed row `updated` and `last_seen` move with it.

### 5. Export stamps and taxonomy pins: STIX `identity` and MISP timestamps move

`taxonomy_versions` now also carries `owasp_dsgai: "2026"`, `maestro: "1.0"`
and `nist_ai_rmf: "1.0"` (`data/stats.json`, `build_manifest.json`,
`genai_incidents.taxonomy_versions()`, the STIX `identity` object's
`x_taxonomy_versions`, the Hugging Face card, and three new MISP machinetags
per event). `mappings/nist_ai_rmf.json` `version` is now the short `"1.0"` (the
description moved to a new `edition` field). Because pin changes must be
visible to clients that dedupe on (`id`, `modified`), the STIX `identity`
`modified` and every MISP event `timestamp` now add an append-only `REVISIONS`
term (rows 3 and 4 are in this release). Per the CHANGELOG's measurement
against the previous `main`, 1 of 65,304 STIX objects changes content and its
`modified` moves by 1 ms, and 31 of 31 MISP events gain tags and move 1 second
each. Both figures are carried, not re-measured (see the last paragraph).

### 6. Corpus labels on AIID rows: 174 new rows are `security`, and 6 existing rows flipped `ai-harm` to `security`

All 174 AIID rows added in this release carry `corpus: security`, and 6
existing AIID rows moved from `ai-harm` to `security` when the AIID side of the
freeze was lifted (D114): INC-01371, INC-04094, INC-04801, INC-07170,
INC-08167 and INC-08169 (facial-recognition misidentification cases). The
cause, per the committed audit
`docs/audits/aiid-corpus-classifier-2026-11-24.md`, is a classifier artifact:
the AIID corpus rule matched the substring `rce` inside "enfo**rce**ment" and
"Reinfo**rce**d", and 786 of 1,645 AIID rows are `security` only through the
rule's no-match fallthrough. **This release does not fix the labelling.**
One row (INC-07572) is pinned back to `ai-harm` by a curation override (O1).
The word-boundary fix to `scripts/scrape_aiid.py` (D155) is merged but takes
effect on the next networked AIID refresh, not in this release's data, and a
mass relabel waits on a second-annotator study (D154) and a user ruling on the
option. Consumers who split on `corpus` should treat the AIID `security`
population as unreliable at the margin; the audit samples the error rate. The
weekly refresh PR now flags every corpus change as `needs-ruling` (D156(a),
D158), so a recurrence is no longer silent.

### 7. The landmark tier and `confidence`: 43 rows demoted to `quality_tier: auto`

The D130-2 and D130-3a reference remediation demoted the corrected rows to
`quality_tier: auto` (ruling D130(c); never promoted): 43 rows changed
`quality_tier` (33 `reviewed` to `auto`, 10 `curated` to `auto`). Nine rows
left the landmark tier by that demotion (`tier` is derived), so
`landmark_count` is **2,080**, not 1,915 plus the 174 new AIID rows (that sum
is 2,089; the difference is the nine). Consumers keyed on `tier: landmark` or
on `confidence` (which derives from `quality_tier`) will see these rows move;
`confidence` changes on 31 rows.
