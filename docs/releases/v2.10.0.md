## Headline — the OWASP migration is a silent breaking change

`owasp_llm` codes migrated from the OWASP Top 10 for LLM Applications
**2025** edition to the **2026** edition (published 2026-08-03) in commit
[`19fa2986`](https://github.com/emmanuelgjr/genai_incidents/commit/19fa2986ce1b316c8291e3ae93f8513532df6557).
The 2026 revision is a renumbering plus one rename — nothing added, nothing
removed — so it is a bijection over `LLM01`–`LLM10`.

**The code space is identical before and after, which is what makes this
dangerous.** `LLM03` is still a valid code today, and it now means
*Excessive Agency* instead of *Supply Chain*. There is no schema violation,
no error, and no CI failure from reading either edition's codes — and **no
way for a downstream reader to tell which edition a given file uses except
by the release it came from.**

**If you filter, join, or alert on literal `owasp_llm` codes, re-check that
logic against the table below before trusting output produced against data
from this release onward.**

| 2025 code | Name (2025) | → | 2026 code | Name (2026) | Move |
|---|---|---|---|---|---|
| `LLM01` | Prompt Injection | → | `LLM01` | Prompt Injection | — |
| `LLM02` | Sensitive Information Disclosure | → | `LLM02` | Sensitive Information Disclosure | — |
| `LLM03` | Supply Chain | → | `LLM04` | Supply Chain | −1 |
| `LLM04` | Data and Model Poisoning | → | `LLM05` | Data and Model Poisoning | −1 |
| `LLM05` | Improper Output Handling | → | `LLM10` | Improper Output Handling | **−5** |
| `LLM06` | Excessive Agency | → | `LLM03` | Excessive Agency | **+3** |
| `LLM07` | System Prompt Leakage | → | `LLM08` | **Hidden Context Exposure** (renamed, widened) | −1 |
| `LLM08` | Vector and Embedding Weaknesses | → | `LLM09` | Vector and Embedding Weaknesses | −1 |
| `LLM09` | Misinformation | → | `LLM07` | Misinformation | +2 |
| `LLM10` | Unbounded Consumption | → | `LLM06` | Unbounded Consumption | **+4** |

**Corpus-wide: 17,498 code assignments across 11,556 of 13,060 entries were
rewritten.** Both figures re-derived directly (see Verification) and match
this document's own audit record exactly.

**Re-classification is explicitly NOT part of this migration.** Several
2026 entries widened their scope (for example, `LLM03` Excessive Agency now
explicitly covers agentic over-permissioning). Incidents that would newly
qualify under a widened entry were **not** added — that would require
re-running classifiers over incident text, which is annotation work (WS2),
not a code renumbering, and is deliberately out of scope here.

**A migration this dangerous needed its own tripwire, and it caught a real
defect.** The migration was verified against a control build — a clean
worktree at the pre-migration commit, rebuilt with the pre-migration
pipeline and inputs, compared entry-by-entry against the migrated output.
That control caught 9 entries (16 code assignments) that an
inputs-only migration had missed, because `merge_and_dedupe.py`'s
retain-on-drop step carries some entries verbatim out of the *previous*
`data/incidents.json` rather than re-deriving them from ingest inputs — so
those rows are a build input the migration script's first pass didn't
touch. The totals still matched exactly before this was caught; only the
distribution had shifted. Recorded in the audit above so future taxonomy
migrations account for that third input class.

## Operational fixes, all merged

- **The weekly refresh was silently dead for eight consecutive runs.**
  `auto-refresh`'s Persist step shallow-cloned with `--depth 1` (implying
  `--single-branch`), so `origin/refresh-state` was never fetched and the
  checkout died `exit 128` on every scheduled run from **2026-07-26 through
  2026-09-13** — rebuild, tests, and the refresh PR were all skipped, with
  no visible failure surfaced anywhere else. Fixed in
  [`05f536ff`](https://github.com/emmanuelgjr/genai_incidents/commit/05f536ff554395f474dce05a8d2ae9b1faf17026)
  with an explicit refspec and a local-fixture regression suite. **This is
  why the corpus has not grown since 2026-07-27** — it is not evidence the
  project went quiet, it is evidence one CI step was silently broken.
- **OECD AI Incidents and Hazards Monitor (AIM) pages over 800 KB were
  silently truncated.** `fetch_page()` sliced the raw response to the first
  800,000 bytes before decoding; a page whose embedded JSON state blob
  started at or straddled that offset was cut mid-tag or mid-JSON and
  folded into "unparseable" with no distinguishing signal from a genuinely
  broken page. Measured at gate: 7 of 250 sampled oversized pages all
  failed after truncation and parsed fine in full; on the 2026-09-14 full
  crawl this silently dropped roughly 38 real incidents per run. Fixed in
  [`9bbec137`](https://github.com/emmanuelgjr/genai_incidents/commit/9bbec13744df79ab083b70a20305cfc5158e0a56)
  by removing the cap (the full body was already downloaded and cached;
  only the parser's view of it was truncated). No data, schema, or ingest
  file was touched by this fix — parser-integrity only.
- **OECD AIM crawl budget.** Merged
  [`eb9788ab`](https://github.com/emmanuelgjr/genai_incidents/commit/eb9788aba2a56c27413a36ffc8baa298c9f0adaf):
  OECD's sitemap carries a legacy all-numeric incident-slug scheme
  alongside the modern date-hash scheme; every legacy-slug page ever
  fetched has failed the parser's body-shape check (0 exceptions observed
  across the whole corpus). The crawl now partitions those URLs out
  **before** they enter the fetch pool rather than spending a rate-limited
  request on each and discarding the result. Live-measured against the
  real sitemap on 2026-09-17: **1,773 of the 3,000-URL crawl window** were
  legacy numeric slugs — roughly 59% fewer requests to `oecd.ai` per run,
  and about 36 minutes of headroom recovered against the workflow's
  60-minute timeout. Frame the benefit honestly: this reduces load on a
  third party's server, it does not change what data ships. No data or
  schema file was touched.
- **`--verify` became a real gate on the rebuilt corpus.**
  [`3f634a05`](https://github.com/emmanuelgjr/genai_incidents/commit/3f634a057e52bb95e5d4f8b571f1dc3559e2c660)
  fixed `--verify` printing a census and returning success unconditionally
  — the expected count it compared against was read but never actually
  written, so the check could not fail. It now records the expected
  post-transform census at apply time and fails closed if a rebuild
  doesn't reproduce it; confirmed to fail by deliberately corrupting one
  expected count.

## Two disclosures this release would be dishonest to omit

### 1. The corpus is frozen by policy — this version bump does not mean new data

**Entry count is unchanged from v2.9.0: 13,060 entries, 1,905 landmark-tier.**
No row was added or removed by this release. OECD AIM refresh merges have
been **frozen since 2026-09-15** under board ruling D25(a), pending (1) a
fix for a query-string URL-collapse bug in `normalize_url()` that has been
silently merging unrelated incidents together, and (2) a review of every
new "merged" deprecation a refresh would write, because deprecations are
append-only and a wrong merge cannot be quietly undone. **Do not infer from
the version number that the underlying data is newer or larger than
v2.9.0's — it is neither.**

**What this release does NOT contain: remediation of the over-merge
already in the published corpus.** The `normalize_url()` fix for *future*
builds has passed independent review but is deliberately held unmerged
until after this cut, specifically so this release does not change any
published ID. Separately, and out of scope here entirely, the design for
*unmerging* the roughly 301 rows the published corpus already collapsed
together (re-deriving the corpus with the fixed key produces 13,361 unique
rows against today's 13,060 — that +301 is the size of the population a
future unmerge would split back out, across 47 currently-published rows
that would become more than one row each) is intentionally deferred to a
separate, designed task because it changes published IDs and needs its own
ruling before any data moves. **Published IDs and redirects are unchanged
by v2.10.0.**

### 2. `generated` understates how current the corpus content actually is

`data/incidents.json` and `data/stats.json` both carry `generated:
2026-07-31`. The maximum `updated` value across every entry in the corpus
is also `2026-07-31`. **Neither of those dates reflects that corpus content
changed on 2026-08-17**, when the OWASP migration rewrote `owasp_llm`
values on 11,556 entries.

Why: `merge_and_dedupe.py` computes `generated` as "today, only if some
entry's own `updated` field equals today's date during this build run;
otherwise carry the previous value forward" (so that a build re-run on a
later calendar day with no real content change doesn't make the drift
checks flap). The OWASP migration was applied by a dedicated migration
script directly to already-committed data, not through a `merge_and_dedupe.py`
run that would have stamped `updated: 2026-08-17` on the changed rows — so
neither `generated` field nor any per-row `updated` field was ever touched
by it. **The practical consequence: nothing in the corpus's own
machine-readable date fields lets a consumer detect that 2026-08-17 content
change at all.** The only place it is dated is this release, the CHANGELOG,
and the migration audit linked above. If you need to know whether your copy
of the data predates the OWASP migration, the release/tag you pulled it
from is the only reliable signal — not any date field inside the file.
**This is not being "fixed" here** — changing a date field is itself a data
change and is out of scope for a release-notes document.
