## Read this first: `incident_count` now excludes retracted entries

Before this release the file's header said `incident_count: 13361` and
`len(incidents) == 13361`; nothing could make those differ. Now an entry can
be **retracted** (below), and the two numbers part ways:

| | v2.11.0 | v2.12.0 |
|---|---:|---:|
| `incident_count` | 13,361 | **15,637** |
| `retracted_count` (new) | absent | **29** |
| `len(incidents)` in `data/incidents.json` | 13,361 | **15,666** |

`len(incidents) = incident_count + retracted_count` (15,637 + 29 = 15,666).
User ruling D44: `incident_count` means "incidents that stand".

**What breaks:**

- Code asserting `len(incidents) == incident_count` now fails. Assert
  `len(incidents) == incident_count + retracted_count`.
- `genai_incidents.load_incidents()` and `data/incidents.min.json` return all
  15,666 rows **including the 29 retracted ones**. Filter them out for
  analysis: `[e for e in load_incidents() if e.get("status") != "retracted"]`
  gives the 15,637 that stand. Absence of `status` means the entry stands.
- STIX, MISP, TAXII, the Hugging Face export and the site **drop** the 29
  (the STIX bundle holds 15,637 `x-genai-incident` objects); the slim JSON
  and the full JSON keep them, with `status`.
- Of the 2,305 new entries, all are `tier: feed`, so the landmark count
  (1,915) is unchanged.

Per invariant 1 this document never adds incidents, vulnerabilities and
capabilities into one number: `incident_count` is the project's own stat, and
the vulnerability/other split is shown beside it wherever it matters.

## Headline 1 — wave 1–2 sources: AVID, cvelistV5 (with the huntr CNA slice), arXiv cs.CR

Approved by the user as D40. **+2,305 new entries, IDs `INC-14911` to

changed by this ingest.** Every new entry is `quality_tier: auto`,
`tier: feed`, `confidence` derived per entry (2,070 medium, 131 low, 104 high): machine-ingested, no human review (user
ruling D43). Of the 2,305: 2,250 are `vulnerability-disclosure`, 55 are
`research`; all are in the `security` corpus (none in `ai-harm`).

| Origin of the new entries | Entries |
|---|---:|
| cvelistV5 only | 2,046 |
| AVID and cvelistV5 (same CVE, folded into one entry) | 104 |
| AVID only | 100 |

(Rows emitted by the three ingests, 270 + 2,502 + 55, exceed the 2,305 entries

### Do not read this as 2,305 entries of new-source coverage

**1,374 of the new vulnerability entries (60% of the 2,305 and 61% of the
2,250 vulnerability entries) are dated after 2026-06. Most of those fill a
gap in the corpus's own stalled NVD refresh; they are not coverage that
cvelistV5, AVID or arXiv brought and NVD lacked.** Only 876 new vulnerability
entries are dated 2026-06 or earlier (857 in 2024-01 to 2026-06, 19 earlier; the
ingest window is by publication date). The honest framing
of what the new sources contributed is therefore the backlog slice plus the
AVID third-party reports (87 rows) and the arXiv papers (55), not the
headline +2,305. Within the backlog window, the cvelistV5 filter matched
3,231 records of which 2,095 (65%) were already in the corpus; the audit's
catch-up figure for the post-2026-06 window is 1,377 emitted rows (1,374
entries; the other 3 rows are suppressed at merge).

### How selection works, and what it costs

- **AVID** (`avidml/avid-db`, MIT): ingested from the repo tarball, never the
  website. 270 rows emitted. The 556 `LLM Evaluation` reports are automated
  garak scan results and are not emitted (benchmark runs are excluded by
  `INCLUSION.md`). 87 third-party reports carry original deterministic prose
  and the MIT marker; the CVE-class rows carry CNA text under the CVE Terms of
  Use, not MIT.
- **cvelistV5** (CVE Program, CVE-TOU): the baseline release zip, filtered by
  `scripts/ai_relevance.py`, which applies the repo's own vocabularies so
  that weak tokens never decide alone and description-only matches need a
  second signal. 2,502 rows emitted. **huntr** enters only as CVE records
  whose assigner is the huntr CNA; huntr.com report text is not ingested and
  nothing from huntr.com is fetched. 368 of the new entries carry the `huntr`
  tag (447 huntr rows were emitted; the other 79 are suppressed at merge). The WS4-T4 allowlist does
  not exist yet; a curated seed of 88 products stands in for it.
- **arXiv cs.CR** (metadata via OAI-PMH, CC0): **deterministic selection
  only, no human-approved list (D43).** The shipped filter selected 55 papers
  and recovers only 6 of the 115 hand-curated arXiv rows' records, so it picks
  a different population from the curated list (attack papers that claim a
  real-world or deployed target, not the famous method papers). Abstracts are
  used by the filter and discarded; each shipped `description` is original
  deterministic prose (`description_provenance: original`), so the "authors'
  prose is not covered by arXiv's CC0" residual does not arise.
- **Skipped on purpose**, with the crosswalk kept offline in the provenance
  files: AVID rows whose CVE is already in the corpus (498) or that would fold
  into an existing entry (7); cvelistV5 rows already in the corpus (2,139) or
  that would fold (65). Folding rewrites the existing entry, and the first
  builds did exactly that to 59 entries before the design changed, so
  **existing entries are not enriched by these sources in this release.** AVID's
  taxonomy has no schema home yet.
- **410 emitted rows (352 cvelistV5, 58 AVID; 79 of them huntr) are suppressed
  at merge** because their CVE ids are on the issue-#88 out-of-scope key list
  (`data/issue88_remediation.json`). They never reach the corpus, and none of
  their CVE ids is on any entry. That is 14% of the cvelistV5 rows the AI filter
  emitted; whether some of them are wrongly on the out-of-scope list is a
  maintainer question this release does not settle.
- **EUVD (ENISA) is NOT ingested.** The licence is unresolved, outreach is
  drafted and not sent, and no EUVD field entered the corpus.

## Headline 2 — 29 entries retracted because the CVE Program REJECTED their CVEs (WS4-T2)

A full sweep of the 6,998 CVE ids carried by the corpus **before wave 1–2**
against the CVE record found **37 REJECTED** (6,953 PUBLISHED; 8 not in the CVE
List at all). All 37 are also `Rejected` in NVD. **The sweep does not cover the
wave 1–2 entries:** the integrated corpus carries 9,169 distinct CVE ids, the
sweep file holds 6,998 of them, and 0 of the 2,171 CVEs on the 2,305 new
entries. The 2,150 cvelistV5-sourced CVEs on the new entries were PUBLISHED at ingest (that ingest drops every non-PUBLISHED record), and the 21 CVEs that reach new entries only through AVID have no recorded rejection state yet; the next refresh checks never-checked ids first.

- **29 entries are `status: retracted`**: every CVE on the entry is rejected
  and every source id is one of those CVEs. **Nothing was deleted; every
  `INC-*` ID still resolves** (invariants 3 and 9). Retracted entries are
  omitted from the `INCIDENTS.md` tables and charts, the site and the
  STIX/MISP/TAXII/Hugging Face feeds; their year-shard cards stay, bannered
  `RETRACTED`, so `#inc-NNNNN` anchors keep working.
- **6 entries are flagged only** (`rejected_cve_ids`): they carry a rejected
  CVE but stand on other, still-published evidence. The rejected id stays in
  `cve_ids` so nothing is lost; the flag says not to trust it.
- **4 of the 29 were rejected as duplicates of another CVE**, not as
  non-issues: `INC-11766`, `INC-11565`, `INC-11750` and `INC-10642`. For
  `INC-10642` the canonical CVE (CVE-2023-48022) is in the corpus. **For the
  other three the canonical CVE (CVE-2021-29421, CVE-2020-15178,
  CVE-2020-36534) is not in the corpus, so the underlying vulnerability is no
  longer counted anywhere.** The retraction stands because the entry's only
  identifier is rejected; re-pointing those three to their canonical CVE is a
  recorded follow-up, not part of this release.
- **STIX and MISP no longer emit rejected CVEs as `vulnerability` objects,
  `exploits` relationships or MISP vulnerability attributes**, for the 29 and
  for the 7 rejected CVEs on the 6 flagged entries. STIX incident objects gain
  `x_rejected_cve_ids` (non-empty on exactly the 6 flagged entries; the 29 are
  not emitted at all). `x_cve_ids` is unchanged.
- **New optional schema fields** (additive): `status`, `status_reason`
  (`{code: "cve-rejected", as_of}`), `rejected_cve_ids`. `status` is emitted
  only when non-default, so the other 15,637 rows gain no `status`. Both schema
  copies are identical.
- **How it stays current:** `scripts/ingest_cve_rejections.py` writes
  `ingest/cve_rejections.json`; the merge applies the rule offline on every
  build and sheds the marker if a CVE is later un-rejected. The two scheduled
  refresh workflows now run it.
- **What it is not:** this delivers the REJECTED half of WS4-T2. CVSS
  rescores, AIID edits and downward severity revisions remain open.

## Licensing and conduct changes

  6.1 (AVID), 6.2 (cvelistV5 including the huntr CNA slice), 6.3 (arXiv

- **`NOTICE-DATA` (and `.reuse/dep5`):** the CVE Terms of Use notice and the
  AVID MIT notice are added. The CVE notice condition applied to the existing
  NVD-derived corpus before this release; it is now met.
- **Row 2.4 (OSV.dev) corrected in place.** An earlier sentence said every OSV
  database reachable by the script is CC-BY 4.0. That was false: OpenSSF
  Malicious Packages (`MAL-` ids) are Apache-2.0. `MAL-` records are now
  excluded from the OSV ingest path; the one committed `MAL-` row dropped
  from the ingest file and the other kept as a bare identifier. The published
  corpus rows were not changed by this (the integration delta shows no change
  to any existing entry outside the 35 above).
- **`ingest/common.py`:** redirect targets (for example a GitHub release asset
  redirecting to its CDN) are now robots-checked and rate-limited like any
  other fetch; before, only the first host was. New `fetch_to_file` streams
  large downloads with robots check, pacing, retry and a `.part` rename.

## Known limitations

- **The OECD/AIID weekly refresh is still frozen** (D25(a), kept by D42). A
  refresh is built but not in this release; it needs a rebuilt `data/` and a
  human review of 17 proposed changes first. The latest `last_seen` on any
  OECD- or AIID-sourced entry that predates this release is 2026-09-18.
- **The AIRI Navigator ingest has been dead since 2026-05-31** (the site was
  relaunched and the data file is gone); it needs a redesign and a licence
  re-read.
- **The existing CVE/GHSA feed has an open precision audit (N9).** A gate
  measured roughly 48% precision on a 40-row sample of the pre-existing feed.
  That is separate from, and larger than, the new-source work here, and it is
  not fixed by this release. The new cvelistV5 rows were read at 40 of 206
  description-only rows plausible, 0 clear false positives, 1 borderline, but
  that is a different population.
- **The new entries are `auto` tier and unreviewed.** A deterministic filter
  chose them; treat them as a feed, not as curated incidents.
- Rejection state covers the 6,998 CVEs that were in the corpus before wave
  1–2, as a snapshot of 2026-10-03; it does not cover the 2,171 CVEs on the new
  entries (2,150 were PUBLISHED at cvelistV5 ingest; 21 AVID-only CVEs have no
  recorded state). A CVE rejected afterwards is caught by the next refresh, not
  by this release.
